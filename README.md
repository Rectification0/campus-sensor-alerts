# Campus Sensor Monitoring & Alerts

Backend service for **GDG Backend Task 1**. It:
- ingests campus sensor readings, singly or in batches, and handles bursts of **10,000 readings in one second**;
- evaluates organizer-defined alert rules, per reading or over a time window;
- lets organizers view, acknowledge and resolve the resulting alerts.

It also includes a sensor simulator and a load-test harness with a written report.

**Stack:** Node.js + TypeScript, Fastify, PostgreSQL 18.

| Brief requirement | Where |
|---|---|
| Single and batch readings | `POST /api/v1/readings`, `POST /api/v1/readings/batch` |
| Bursts of 10,000 readings/second | Group-commit ingestion; see the [load-test report](docs/LOAD_TEST_REPORT.md) |
| Create, edit, enable, disable rules | `/api/v1/rules` endpoints |
| Single-reading and time-window rules | `THRESHOLD` and `WINDOW` (avg/min/max) rules |
| Alerts when a rule is satisfied | One active alert per rule and sensor, with a trigger count |
| View, acknowledge, resolve alerts | `/api/v1/alerts` endpoints |
| Sensor simulator | `pnpm sim` |
| Load-test report | [`docs/LOAD_TEST_REPORT.md`](docs/LOAD_TEST_REPORT.md), regenerated by `pnpm loadtest` |
| Architecture and trade-offs | [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) |

Out of scope, per the brief: frontend, dashboard, authentication, notifications.

---

## Prerequisites

- **Node.js 22.9 or newer** (developed on 24.12)
- **pnpm 11.** `corepack enable` picks the pinned version from `package.json`. Alternatively: `npm install -g pnpm@11`.
- **PostgreSQL 18 or newer**, running and reachable. The schema uses PostgreSQL 18's built-in `uuidv7()`.

Examples use a POSIX shell: macOS/Linux, or Git Bash on Windows.

## Setup

```sh
git clone https://github.com/Rectification0/campus-sensor-alerts.git
cd campus-sensor-alerts
pnpm install

cp .env.example .env
# Edit .env: set the PostgreSQL password in DATABASE_URL and TEST_DATABASE_URL.
# URL-encode special characters, e.g. "p@ss" becomes "p%40ss".

pnpm db:create      # creates the database named in DATABASE_URL (if missing)
pnpm db:migrate     # applies src/db/migrations/*.sql
```

## Run

```sh
pnpm dev                    # development, auto-reload (tsx watch)

pnpm build && pnpm start    # production build
```

The server listens on `http://127.0.0.1:3000` (`PORT` in `.env`). At startup it:
1. checks the database connection;
2. refuses to start if migrations are pending;
3. loads the rules and rebuilds time-window state from stored readings.

`Ctrl+C` shuts down gracefully: queued readings are committed first.

## API

Base path `/api/v1`. JSON in and out. Timestamps are ISO-8601 with a timezone and are returned in UTC.

| Method | Path | Purpose | Success | Errors |
|---|---|---|---|---|
| POST | `/readings` | Ingest one reading | `202` | `400`, `503` |
| POST | `/readings/batch` | Ingest 1–1000 readings (partial acceptance) | `202` | `400`, `413`, `503` |
| POST | `/rules` | Create a rule | `201` | `400` |
| GET | `/rules`, `/rules/:id` | View rules | `200` | `404` |
| PATCH | `/rules/:id` | Edit a rule | `200` | `400`, `404` |
| POST | `/rules/:id/enable`, `/rules/:id/disable` | Enable / disable (idempotent) | `200` | `404` |
| GET | `/alerts?limit=&cursor=` | List alerts, newest first | `200` | `400` |
| GET | `/alerts/:id` | View one alert | `200` | `404` |
| POST | `/alerts/:id/acknowledge` | `OPEN → ACKNOWLEDGED` | `200` | `404`, `409` |
| POST | `/alerts/:id/resolve` | `OPEN`/`ACKNOWLEDGED → RESOLVED` | `200` | `404` |

**What the status codes guarantee:**
- **`202`:** the readings, and any alert they triggered, are committed to the database.
- **`503`** (buffer full, or database unavailable for ~5 s): nothing from that request was stored. Retry after `Retry-After` seconds.

### Examples

```sh
API=http://127.0.0.1:3000/api/v1
```

**Create rules.** A single-reading threshold rule, and a 10-minute average rule:

```sh
curl -s -X POST $API/rules -H 'content-type: application/json' \
  -d '{"kind":"THRESHOLD","type":"temperature","operator":"gt","threshold":30}'

curl -s -X POST $API/rules -H 'content-type: application/json' \
  -d '{"kind":"WINDOW","type":"temperature","operator":"gt","threshold":28,"aggregation":"avg","windowSeconds":600}'
```

```json
{"id":"01a14…","kind":"THRESHOLD","type":"temperature","operator":"gt","threshold":30,"aggregation":null,"windowSeconds":null,"enabled":true,"createdAt":"…","updatedAt":"…"}
```

- **Rule fields:**
  - `kind`: `THRESHOLD` or `WINDOW`
  - `operator`: `gt`, `gte`, `lt` or `lte`
  - `aggregation`: `avg`, `min` or `max` (WINDOW only)
  - `windowSeconds`: 10–86400 (WINDOW only)
- **Scope:** a rule applies to every sensor reporting its `type`, and is evaluated per sensor.

**Send readings:**

```sh
curl -s -X POST $API/readings -H 'content-type: application/json' \
  -d '{"sensorId":"library-floor-2","type":"temperature","value":34.5,"timestamp":"2026-10-12T10:30:00Z"}'
# {"accepted":1}

curl -s -X POST $API/readings/batch -H 'content-type: application/json' -d '[
  {"sensorId":"lab-floor-1","type":"temperature","value":27,"timestamp":"2026-10-12T10:30:00Z"},
  {"sensorId":"lab-floor-1","type":"temperature","value":"hot","timestamp":"2026-10-12T10:31:00Z"}
]'
# {"accepted":1,"rejected":[{"index":1,"errors":[{"path":"/value","message":"must be number"}]}]}
```

**Edit, disable and enable a rule:**

```sh
RULE_ID=<id from the create response>
curl -s -X PATCH $API/rules/$RULE_ID -H 'content-type: application/json' -d '{"threshold":32}'
curl -s -X POST $API/rules/$RULE_ID/disable
curl -s -X POST $API/rules/$RULE_ID/enable
curl -s $API/rules
```

**View and manage alerts:**

```sh
curl -s "$API/alerts?limit=10"
# {"items":[{"id":"…","ruleId":"…","sensorId":"library-floor-2","type":"temperature","status":"OPEN",
#   "triggerValue":34.5,"lastValue":34.5,"triggerCount":1,"windowStart":null,"windowEnd":null,
#   "firstTriggeredAt":"2026-10-12T10:30:00.000Z",…}],"nextCursor":null}

ALERT_ID=<id from the list>
curl -s $API/alerts/$ALERT_ID
curl -s -X POST $API/alerts/$ALERT_ID/acknowledge     # status ACKNOWLEDGED
curl -s -X POST $API/alerts/$ALERT_ID/resolve         # status RESOLVED
curl -s -X POST $API/alerts/$ALERT_ID/acknowledge     # 409: cannot acknowledge a RESOLVED alert
```

Pagination: pass the response's `nextCursor` as `?cursor=`. `limit` is 1–200 (default 50).

**Errors:**

```json
{"statusCode":400,"error":"Bad Request","message":"…","errors":[{"path":"/aggregation","message":"is required for WINDOW rules"}]}
```

**Alert behaviour:**
- While an alert for a (rule, sensor) is `OPEN` or `ACKNOWLEDGED`, further matches increase its `triggerCount` instead of creating duplicates.
- After it is `RESOLVED`, the next match opens a new alert.
- Readings older than the newest one already seen for a sensor are stored and checked by threshold rules, but don't enter time windows.

## Sensor simulator

```sh
pnpm sim --help

# Continuous traffic: 20 sensors x 3 types, 200 readings/s for 30 s, occasional spikes
pnpm sim --sensors 20 --rate 200 --duration 30 --pattern spike

# A burst of exactly 10,000 readings
pnpm sim --burst 10000 --sensors 200 --mode batch --batch-size 1000
pnpm sim --burst 10000 --sensors 200 --mode single --connections 512
```

| Pattern | Behaviour | Typical use |
|---|---|---|
| `normal` | Realistic random walk per type (temperature 22 ± 3 °C, humidity 45 ± 10 %, CO₂ 600 ± 150 ppm) | Background traffic |
| `spike` | ~2% of values jump 3–4 ranges above normal (e.g. 31–34 °C) | Triggers threshold rules |
| `drift` | Rises one range per minute | Triggers time-window rules within minutes |

Sensor ids look like `library-floor-2`. Each run prints accepted/rejected counts, HTTP statuses and latency percentiles; `--json` prints machine-readable output.

## Tests

```sh
pnpm db:test:reset   # creates and migrates the test database (TEST_DATABASE_URL)
pnpm test            # all tests (unit + integration)
pnpm test:unit       # unit tests only, no database needed
pnpm test:int        # integration tests against TEST_DATABASE_URL
pnpm lint && pnpm typecheck
```

Integration tests reset the test database themselves; it only has to exist. Coverage includes:
- every endpoint;
- the guarantee that a `202` arrives only after the reading is stored;
- `503` behaviour, both when the buffer is full and when the database is down;
- graceful shutdown;
- window rules using history from before a rule existed and across a restart;
- alert de-duplication and every lifecycle path;
- a simulator run against a live server.

## Load test

```sh
pnpm loadtest
```

What it does:
1. Builds the server and runs it against a **separate** database, `campus_sensors_loadtest`, recreated on every run.
2. Seeds 24 rules and warms up.
3. Fires three burst shapes of 10,000 readings, three runs each.
4. Verifies that the stored row count matches the accepted count.
5. Rewrites the results section of [`docs/LOAD_TEST_REPORT.md`](docs/LOAD_TEST_REPORT.md).

Results on a 15 W laptop (client, server and PostgreSQL on one machine; durability on):

| Burst | Completion | Result |
|---|---|---|
| 10 × 1,000-reading batches | 0.14–0.32 s | passes every run |
| 100 × 100-reading batches | 0.19–0.44 s | passes every run |
| 10,000 single readings | 0.81–3.39 s | passes most runs |

**About the single-reading result:**
- **What always held:** no failed requests, and every reading was stored, in every run.
- **What sometimes didn't:** the p99 < 2 s target held in 6 of 11 validation runs, and completion < 3 s in 9 of 11.
- **Why:** on this machine the per-response socket write is the bottleneck. The report has the profile and the full numbers.

**Tip:** a burst against a freshly started server is slower, because of code warm-up and connection setup; the load test warms up first.

Options:
- `--runs N`
- `--scenarios A,B,C`
- `--single-connections N`
- `--no-report`
- **Server settings** pass through from the environment, e.g. `FLUSH_CONCURRENCY=1 pnpm loadtest --no-report`.

## Configuration

Set in `.env`; see `.env.example`.

| Variable | Default | Meaning |
|---|---|---|
| `PORT` | `3000` | HTTP port (binds 127.0.0.1) |
| `DATABASE_URL` | required | PostgreSQL connection string |
| `TEST_DATABASE_URL` | none | Database for integration tests |
| `LOADTEST_DATABASE_URL` | `…/campus_sensors_loadtest` | Database for `pnpm loadtest` (recreated) |
| `PG_POOL_MAX` | `10` | Connection pool size |
| `BUFFER_CAPACITY` | `100000` | Max queued readings before `503` |
| `FLUSH_MAX_ROWS` | `2000` | Max readings per transaction |
| `FLUSH_INTERVAL_MS` | `10` | Max wait before committing a partial batch |
| `FLUSH_CONCURRENCY` | `3` | Overlapping transactions |
| `COMMIT_RETRY_BUDGET_MS` | `5000` | Retry time for a failing commit before `503` |
| `BATCH_MAX_ITEMS` | `1000` | Max readings per batch request |
| `BODY_LIMIT_BYTES` | `1048576` | Max request body (`413` above) |
| `LOG_LEVEL` | `info` | `debug` adds per-batch timings |
| `REQUEST_LOGGING` | `true` | Per-request logs (off for load tests) |
